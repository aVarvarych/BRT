# Погані дороги — опис продукту

> Статус: погоджено за результатами обговорення 2026-10-08/09. Документ живий — змінюємо разом із рішеннями.

## 1. Ідея

Водій їде знайомою дорогою, наприклад Київ — Іллінці, і по дорозі одним дотиком відмічає ями та розбиті ділянки. Наступного разу на цьому маршруті застосунок заздалегідь попереджає звуком, голосом і на екрані: «Увага, яма через 300 метрів».

**Кому:** водіям, які регулярно їздять тими самими маршрутами (траса до батьків, на дачу, у відрядження) і хочуть не влітати в ті самі ями.

**Цінність:** менше пошкоджених дисків і підвіски, спокійніша поїздка. Пам'ятати дорогу «напам'ять» більше не потрібно.

## 2. Основні сценарії

### 2.1. Перша поїздка: запис маршруту

1. Користувач створює маршрут з назвою «Київ — Іллінці».
2. Тисне **«Старт»**. Телефон пише GPS-трек, екран не гасне.
3. Проїхавши яму, тисне велику кнопку **«ПРОБЛЕМА»** на пів екрана. Підтверджень немає, у відповідь звучить короткий звук.
4. Доїхавши, тисне **«Завершити»**.
5. Відкривається **перегляд поїздки**, тобто список міток. Тут уже спокійно можна вказати тип і серйозність кожної мітки або видалити хибну.

Записаний трек і стає маршрутом. Будувати маршрут заздалегідь не треба.

### 2.2. Повторна поїздка: попередження

1. Користувач відкриває маршрут і тисне **«Старт»**. Застосунок завантажує з сервера свіжий **пакет попереджень** (без зв'язку бере збережений).
2. Під час руху застосунок попереджає про відомі проблеми попереду, **в обидва напрямки**: маршрут «Київ — Іллінці» працює і дорогою назад.
3. Нові ями так само відмічаються кнопкою «ПРОБЛЕМА».
4. Якщо яму вже залатали, під час попередження можна натиснути **«Вже нема»**.

Режим один, **«Поїздка»**: він завжди і записує, і попереджає. Під час першої поїздки маршрутом попереджати просто ще нема про що.

## 3. Можливості

### 3.1. Маршрути
- Маршрут створюється тільки з назвою, а його лінія береться з першої записаної поїздки.
- Кожна наступна поїздка додає до маршруту свій трек і свої мітки.
- Маршрут можна перейменувати або видалити.

### 3.2. Запис поїздки
- GPS приблизно раз на секунду. Точки з точністю гірше 30 м і повтори на стоянці відкидаються.
- Під час поїздки екран не гасне (Screen Wake Lock).
- На екрані немає карти, лише великі елементи: кнопка «ПРОБЛЕМА», час, пройдена відстань, кількість міток, якість GPS-сигналу, відстань до найближчої проблеми попереду.
- **Автозавершення:** після 10 хв стоянки з'являється плашка «Ви доїхали? Завершити / Ще їду» з голосовою підказкою. Якщо відповіді немає 30 хв, поїздка завершується сама.

### 3.3. Позначка проблеми
- Один дотик великої кнопки без жодних діалогів.
- **Поправка на реакцію:** між ямою й натисканням минає 1–2 с, а на 90 км/год це 25–50 м. Тому мітка відкочується на 1,5 с назад по треку.
- За замовчуванням нова мітка має тип «Яма» і серйозність «Серйозно». Деталі уточнюються після поїздки.
- **Повторна позначка** ближче 30 м від відомої активної проблеми нової не створює, а додає підтвердження з датою.

### 3.4. Типи та серйозність

| Тип | | Серйозність |
|---|---|---|
| 🕳️ Яма | | Помірно |
| ⚠️ Розбита ділянка | | Серйозно (за замовчуванням) |
| 〽️ Лежачий поліцейський | | Небезпечно |
| 🚧 Ремонт | | |
| ❗ Інше | | |

Серйозність озвучується в голосовому попередженні («Увага, небезпечна яма через 300 метрів»), і від неї залежить, наскільки наполегливий звуковий сигнал.

### 3.5. Перегляд після поїздки
- Відкривається одразу після «Завершити».
- Це список міток, наприклад «🕳️ Яма · 34,2 км від старту · 14:32».
- Кожну мітку можна змінити (тип, серйозність), видалити, а усунену відновити.

### 3.6. Попередження
- **Коли:** приблизно за 12 с до проблеми з поточною швидкістю, але не ближче 150 м і не далі 600 м. Друге коротке пищання за ~50 м.
- **Що саме:**
  - звуковий сигнал;
  - голос українською;
  - велика плашка на весь екран (тип, відстань, що оновлюється наживо, кнопка «Вже нема»).
- **Напрямок:** попереджаємо лише про проблеми **попереду** за курсом руху, але незалежно від того, в якому напрямку їх відмітили.
- **Беззвучний режим iPhone:** попередження звучать і в ньому, бо це питання безпеки. Звук підтвердження позначки в беззвучному режимі мовчить.
- **Розбиті ділянки:** мітки ближче 200 м одна від одної по маршруту об'єднуються в одну ділянку.
  - Звучить одне попередження про той кінець, до якого під'їжджаємо: «Розбита дорога через 300 метрів, довжина 1,2 кілометра».
  - Усередині ділянки плашка показує «ще 800 м поганої дороги».
  - На виїзді звучить короткий сигнал «ділянка закінчилась».
- **«Вже нема»:** проблема стає усуненою й одразу зникає з попереджень. Якщо пізніше відмітити яму на тому самому місці, вона знову стає активною.

### 3.7. Робота без зв'язку
- Пакет попереджень кешується на телефоні, тож попередження працюють без інтернету.
- Точки й мітки збираються в чергу на телефоні. Черга переживає закриття застосунку й відправляється пакетами, коли з'являється зв'язок.

## 4. Обмеження (свідомо прийняті)

Застосунок зроблено як **PWA**, щоб обійтися без App Store, без Xcode і без перевстановлень. Ціна цього рішення:

| Обмеження | Як живемо з цим |
|---|---|
| Працює лише тоді, коли застосунок відкритий і екран увімкнений | Телефон у тримачі на зарядці, екран не гасне, бо ми його не даємо вимкнути |
| Якщо перемкнутися на іншу програму або заблокувати екран, запис і попередження стають на паузу | Після повернення все продовжується, а трек матиме пропуск |
| Навігатор і музику не можна приглушити на час голосового попередження | Наш голос звучить поверх них |
| На iPhone немає вібрації | Є звук і візуальна плашка |
| Немає системних сповіщень | Усі попередження показуються всередині застосунку |

**План Б:** якщо тестова поїздка (див. §8) покаже, що PWA не впорається, переходимо на нативний застосунок (Expo / React Native + Apple Developer за $99 на рік, встановлення через ad-hoc або TestFlight). Логіку попереджень пишемо окремим модулем без залежностей від браузера, щоб її можна було перенести.

## 5. Поза межами першої версії

- Карта в застосунку, прокладання маршрутів, інтеграції зі сторонніми картами й навігаторами.
- Спільна база ям між користувачами. Зараз кожен пристрій бачить лише свої дані, але модель даних зберігає координати й автора, щоб згодом зробити спільний доступ.
- Реєстрація та вхід.
- Голосова команда «яма», Bluetooth-кнопка на кермі.
- Інші мови, крім української.
- Публікація в App Store.

## 6. Архітектура

```
tracker_road/
├── app/        PWA — Vite + React + TypeScript
├── backend/    API — Node.js + Express 5 + TypeScript
└── docs/       документація (цей файл, api.md)
```

### 6.1. Розподіл відповідальності

**Бекенд** робить важку частину:
- прив'язку міток до лінії маршруту («км від старту»);
- поправку на реакцію водія;
- групування міток у ділянки;
- підтвердження повторних позначок;
- формування **пакета попереджень** маршруту.

**Телефон** лише:
- записує трек і мітки;
- відправляє їх пакетами;
- кешує пакет попереджень;
- щосекунди рахує відстань до найближчої проблеми попереду й реагує на неї.

### 6.2. Застосунок (`app/`)
- Vite + React + TypeScript.
- IndexedDB для черги відправки й кешу пакетів попереджень.
- Service worker, щоб застосунок запускався без зв'язку.
- Модуль попереджень на чистому TS, без залежностей від браузера.
- Встановлення: Safari → «Поділитися» → «На екран Додому».

### 6.3. Бекенд (`backend/`)
- Node.js 26, Express 5, TypeScript 6.0, vitest. Dev — `tsx watch`, prod — збирання через esbuild і запуск звичайним `node`.
- **Clean Architecture і SOLID.** Шари `domain` → `application` → `infrastructure` / `presentation`, залежності спрямовані лише всередину, а все збирається в composition root.
- **PostgreSQL 16 + PostGIS**, доступ через **Drizzle**. ORM живе тільки в `infrastructure`.
- **Гео-правила** (групування, підтвердження, прив'язка до маршруту) описуються в `domain` на TypeScript. PostGIS використовується для зберігання, просторових індексів і пошуку поблизу.
- Доменну модель проєктує автор бекенду (окреме рішення).
- Бекенд пише власник проєкту, а Claude допомагає як ментор: пояснює, ставить задачі, рецензує код.

### 6.4. Обмін даними
- Реєстрації немає. Кожен запит містить `X-Api-Key` (статичний ключ сервера, вводиться один раз у налаштуваннях) і `X-Device-Id` (UUID, який пристрій генерує при першому запуску).
- Усі ідентифікатори (маршрут, поїздка, пакет, мітка) генерує телефон як UUID.
- **Пакети:** кожні 30 с або по 200 точок, точки й мітки разом. Пакет видаляється з черги тільки після підтвердження сервера, а повторна відправка того самого `batchId` дублів не створює.
- **Пакет попереджень** завантажується при «Старт» поїздки (без зв'язку береться з кешу). Мітки, додані в поточній поїздці, в ній же попереджень не дають, а сервер перераховує пакет після завершення поїздки.
- **Конфлікти:** перемагає останнє за часом редагування.
- Контракт API описано в [`api.md`](api.md). Під час розробки він може змінюватися.

### 6.5. Інфраструктура
- **Розробка:**
  - бекенд працює прямо на Mac через `tsx watch` (перезапуск при збереженні файлу), у Docker лише PostgreSQL + PostGIS;
  - застосунок працює на Vite dev-сервері з HMR і проксі `/v1` → `localhost:3000`, тож CORS не потрібен;
  - усе разом запускає одна команда `npm run dev` з кореня (`concurrently`);
  - змінні з `.env` читає сам Node (`--env-file-if-exists`), без `dotenv`;
  - щоб перевірити на iPhone, Vite-сервер відкривається через тунель cloudflared.
- **Продакшн:**
  - бекенд збирається через esbuild в `dist/index.js` і запускається звичайним `node`, без TypeScript в образі;
  - VPS з доменом, Docker Compose (`restart: unless-stopped`), міграції виконуються окремим кроком перед стартом API;
  - Caddy з автоматичним HTTPS. Один домен віддає і API, і PWA.
- Git локально. Віддалений репозиторій і CI підключимо на етапі деплою.

## 7. Головні рішення та їх причини

| Рішення | Чому |
|---|---|
| PWA, а не нативний застосунок | Без App Store, Xcode і перевстановлень кожні 7 днів. Обмеження PWA прийнятні, бо під час поїздки застосунок і так на екрані |
| Карти немає | Без сторонніх інтеграцій. За кермом карта лише відволікає, а для перегляду після поїздки вистачає списку з «км від старту» |
| Попередження лише для обраного маршруту | Простіше й передбачуваніше |
| Попередження в обидва боки | Жодна яма не лишиться без попередження. Ціна: зрідка зайві попередження про яму на зустрічній смузі |
| Один дотик, деталі потім | Безпека: за кермом жодних меню |
| Ділянки замість десятків точок | 20 сигналів підряд на розбитій дорозі стали б спамом |
| Важка логіка на бекенді, реакція на телефоні | Правила в одному місці й їх легко змінювати, а попередження все одно працюють без зв'язку |
| PostgreSQL + PostGIS | Задача майже повністю геометрична, а PostGIS — стандарт для таких задач |
| Гео-правила в domain | Clean Architecture: бізнес-правила тестуються без бази й не залежать від інфраструктури |

## 8. План робіт

1. **Тестова сторінка на iPhone** (15 хв поїздки): чи не гасне екран, як працює GPS (точність, швидкість, курс), чи грає звук у беззвучному режимі, чи звучить голос українською. За результатом **остаточно вирішуємо щодо PWA**.
2. Специфікація й контракт API (`docs/api.md`) → затвердження.
3. Застосунок із заглушкою сервера (Claude) **паралельно з** бекендом (власник проєкту, крок за кроком, з рецензією).
4. Підключення до справжнього бекенду, тестова поїздка Київ → Іллінці.
5. Деплой на VPS.

## 9. Відкриті питання

- Доменна модель бекенду: агрегати, межі, назви. Початкову пропозицію подано в §10, автор бекенду уточнює її під час розробки.
- Конкретні значення порогів (200 м для ділянки, 30 м для підтвердження, 12 с для попередження) уточнимо після реальних поїздок. Їх треба зробити налаштовуваними (див. §10.4).

## 10. Сутності та основні дії (план для бекенду)

> Це **пропозиція**, з якої починається розробка, а не остаточна модель. Назви, межі агрегатів і поля автор бекенду може змінювати. Головне, щоб збереглися правила з §3.

### 10.1. Огляд

```
Device 1──* Route 1──* Trip 1──* TrackPoint
                │         │
                │         └──* Mark ──► Problem   (сира позначка → проблема)
                └──* Problem
SyncBatch — журнал прийнятих пакетів (для ідемпотентності)
Section, AlertPackage — обчислюються, не зберігаються
```

Важливо розрізняти **Mark** (сирий факт «водій натиснув кнопку тут і в цей момент») і **Problem** (яма на дорозі, яка живе довше за одну поїздку). Кілька позначок однієї ями в різних поїздках дають одну проблему з кількома підтвердженнями.

### 10.2. Сутності

#### Device: пристрій
Замінює користувача, поки немає реєстрації.

| Поле | Тип | Примітка |
|---|---|---|
| `id` | UUID | з заголовка `X-Device-Id` |
| `firstSeenAt`, `lastSeenAt` | timestamp | |

**Дії:**
- **Розпізнати пристрій:** при першому запиті з невідомим `X-Device-Id` створюється запис, при наступних оновлюється `lastSeenAt`.

**Правила:**
- Будь-які дані (маршрути, поїздки, проблеми) видно тільки пристрою-власнику.

---

#### Route: маршрут (агрегат)

| Поле | Тип | Примітка |
|---|---|---|
| `id` | UUID | генерує телефон |
| `deviceId` | UUID | власник |
| `name` | string | 1–100 символів, обрізати пробіли |
| `line` | LineString \| null | лінія маршруту; `null`, поки не завершена перша поїздка |
| `lineSourceTripId` | UUID \| null | з якої поїздки побудована лінія |
| `createdAt`, `updatedAt` | timestamp | |

**Дії:**
- **Створити маршрут** `(id, name)`. Повторний запит з тим самим `id` не створює дубля, а повертає вже наявний маршрут.
- **Перейменувати маршрут.**
- **Видалити маршрут** разом з усіма поїздками, точками, позначками й проблемами.
- **Список маршрутів** зі статистикою: довжина лінії, кількість активних проблем, кількість поїздок, дата останньої поїздки.
- **Побудувати лінію маршруту:** викликається, коли завершується перша поїздка маршруту. Трек поїздки спрощується (~5 м) і зберігається як `line`.

**Правила:**
- Лінію будує лише **перша завершена** поїздка. Уточнення лінії за новими поїздками відкладаємо на пізніше.

---

#### Trip: поїздка (агрегат)

| Поле | Тип | Примітка |
|---|---|---|
| `id` | UUID | генерує телефон |
| `routeId`, `deviceId` | UUID | |
| `status` | `active` \| `finished` | |
| `finishReason` | `user` \| `auto` \| null | хто завершив: водій чи автозавершення |
| `startedAt`, `finishedAt` | timestamp | |
| `distanceM`, `pointsCount` | number | оновлюються, коли приходять пакети |

**Дії:**
- **Почати поїздку** `(id, routeId, startedAt)`. Якщо в пристрою вже є інша активна поїздка, вона автоматично завершується.
- **Завершити поїздку** `(finishedAt, reason)`. Дія ідемпотентна. Після неї треба побудувати лінію маршруту (якщо це перша поїздка) і перерахувати пакет попереджень.
- **Перегляд поїздки:** позначки поїздки, кожна разом зі своєю проблемою і «км від старту».

**Правила:**
- `finishedAt ≥ startedAt`.
- ⚠️ **Пакети можуть прийти вже після завершення поїздки**, бо черга на телефоні працює без зв'язку. Їх треба приймати, а не відхиляти.

---

#### TrackPoint: точка треку
Це не агрегат, а потік даних, який лише додається.

| Поле | Тип |
|---|---|
| `tripId` | UUID |
| `t` | timestamp (мс) |
| `position` | Point (lat, lng) |
| `accuracyM`, `speedMps`, `headingDeg` | number \| null |

**Правила:**
- Пара `(tripId, t)` унікальна, повторна точка ігнорується.
- Читати точки потрібно лише для двох речей: побудувати лінію маршруту й зробити поправку позначки на реакцію водія.

---

#### Mark: позначка (сирий факт натискання)

| Поле | Тип | Примітка |
|---|---|---|
| `id` | UUID | генерує телефон |
| `tripId`, `deviceId` | UUID | |
| `t` | timestamp | момент натискання |
| `rawPosition` | Point | позиція в момент натискання |
| `position` | Point | після поправки на реакцію |
| `problemId` | UUID | до якої проблеми прив'язана |

Позначки не редагуються й існують окремо від проблем. Саме з них береться історія та підтвердження проблем.

---

#### Problem: проблема на дорозі (агрегат)

| Поле | Тип | Примітка |
|---|---|---|
| `id` | UUID | дорівнює `id` першої позначки, що її створила |
| `routeId` | UUID | |
| `position` | Point | |
| `type` | `pothole` \| `broken` \| `bump` \| `roadwork` \| `other` | за замовчуванням `pothole` |
| `severity` | `moderate` \| `serious` \| `dangerous` | за замовчуванням `serious` |
| `status` | `active` \| `resolved` | |
| `confirmations` | number | скільки позначок до неї прив'язано |
| `firstReportedAt`, `lastConfirmedAt` | timestamp | |
| `resolvedAt` | timestamp \| null | |
| `kmFromStart` | number \| null | рахується, коли є лінія маршруту |
| `updatedAt` | timestamp | для правила «перемагає останнє редагування» |

**Дії:**
- **Зареєструвати позначку.** Це головна дія, вона описана окремо в §10.3.
- **Змінити тип чи серйозність:** застосовується лише тоді, коли час зміни на клієнті новіший за `updatedAt`.
- **Позначити усуненою** («Вже нема»): `status = resolved`, `resolvedAt = now`.
- **Відновити:** `status = active`, `resolvedAt = null`.
- **Видалити:** хибна позначка, видаляється з перегляду поїздки.

**Правила:**
- `resolvedAt` заповнений тоді й тільки тоді, коли `status = resolved`.
- Нова позначка на місці усуненої проблеми робить її знову активною (див. §10.3).

---

#### SyncBatch: журнал прийнятих пакетів

| Поле | Тип |
|---|---|
| `batchId` | UUID (з телефона) |
| `deviceId`, `tripId` | UUID |
| `receivedAt` | timestamp |
| `pointsCount`, `marksCount` | number |

Цей журнал потрібен для ідемпотентності. Якщо `batchId` вже є, сервер нічого не робить і відповідає «прийнято».

---

#### Section: розбита ділянка
Обчислюваний value object, у базі не зберігається.
- Група активних проблем маршруту, де між сусідніми менше 200 м **уздовж лінії маршруту**.
- Поля:
  - `problemIds`;
  - `startKm`, `endKm`, `lengthM`;
  - `polyline` (відрізок лінії маршруту з точками через ~20 м);
  - `worstSeverity`;
  - `types`.
- Проблема без сусідів у межах 200 м у ділянку не потрапляє й лишається точковою.

#### AlertPackage: пакет попереджень
Модель лише для читання, віддається телефону.
- `routeId`.
- `version`: змінюється, коли змінилось хоч щось. Наприклад, береться найбільший `updatedAt` серед проблем маршруту.
- `generatedAt`.
- `problems[]`: точкові активні проблеми (`id`, позиція, тип, серйозність, `kmFromStart`).
- `sections[]`: розбиті ділянки.
- Усунені проблеми в пакет не потрапляють.

### 10.3. Ключові процеси

**Прийом пакета** (`POST /v1/sync/batches`), усе в одній транзакції:
1. Якщо `batchId` вже є в журналі, відповісти «прийнято» і на цьому закінчити.
2. Перевірити, що поїздка існує й належить цьому пристрою.
3. Зберегти точки, пропускаючи дублікати `(tripId, t)`. Оновити `distanceM` і `pointsCount` поїздки.
4. Для кожної позначки виконати **реєстрацію позначки** (див. нижче).
5. Записати `batchId` у журнал.

**Реєстрація позначки:**
1. **Поправка на реакцію:** знайти положення на треку цієї поїздки за `t − 1,5 с` (інтерполювати між сусідніми точками). Якщо потрібних точок немає, взяти `rawPosition`.
2. **Пошук збігу:** знайти найближчу проблему цього маршруту (як активну, так і усунену) в радіусі 30 м.
   - Знайшли активну: `confirmations + 1`, оновити `lastConfirmedAt`.
   - Знайшли усунену: зробити її знову активною, `confirmations + 1`.
   - Нічого не знайшли: створити нову проблему з `id = mark.id`, тип і серйозність за замовчуванням.
3. Зберегти позначку з посиланням на `problemId`.
4. Якщо лінія маршруту вже існує, порахувати `kmFromStart`.

**Завершення поїздки:**
1. Встановити статус і час завершення.
2. Якщо в маршруту ще немає лінії, побудувати її з треку цієї поїздки й перерахувати `kmFromStart` для всіх проблем маршруту.

**Побудова пакета попереджень** (`GET /v1/routes/:id/alert-package`):
1. Узяти активні проблеми маршруту.
2. Відсортувати їх за `kmFromStart`. Проблеми без лінії або ті, що лежать далі 50 м від неї, лишаються точковими.
3. Згрупувати в ділянки (поріг 200 м).
4. Сформувати `version`. Якщо клієнт надіслав ту саму версію, відповісти `304 Not Modified`.

### 10.4. Доменні сервіси та налаштування

| Сервіс (domain) | Що робить |
|---|---|
| `ReactionCompensator` | зсуває позначку на N с назад по треку |
| `ProblemMatcher` | шукає наявну проблему в радіусі R |
| `LinearReferencer` | проєкціює точку на лінію, повертає «км від старту» і відстань до лінії |
| `SectionClusterer` | групує проблеми в ділянки |
| `TrackSimplifier` | спрощує трек у лінію маршруту |

Сервіси залежать лише від інтерфейсу гео-обчислень. Реалізація на TS (або через PostGIS) живе в infrastructure.

Пороги задаються в одному об'єкті конфігурації, а не розкидані по коду:

| Параметр | Значення |
|---|---|
| `reactionDelaySec` | 1,5 |
| `matchRadiusM` | 30 |
| `sectionGapM` | 200 |
| `maxDistanceFromLineM` | 50 |
| `routeSimplifyToleranceM` | 5 |
| `sectionPolylineStepM` | 20 |

Пороги попереджень (12 с, 150–600 м, 50 м) живуть на телефоні.

### 10.6. Порядок розробки бекенду

Кожен крок завершується тестами: unit для domain і application, integration для репозиторіїв і HTTP.

1. **Каркас:**
   - структура шарів, composition root, конфіг з `.env`;
   - Docker Compose з PostgreSQL + PostGIS, Drizzle з першою міграцією;
   - `GET /health`;
   - middleware `X-Api-Key` + `Device`, обробка помилок.
2. **Route:** створити, перейменувати, видалити, список.
3. **Trip:** почати, завершити.
4. **Прийом пакетів:** лише точки, з ідемпотентністю через `SyncBatch`.
5. **Позначки й проблеми:** реєстрація позначки з `ProblemMatcher`, поки без поправки на реакцію.
6. **`ReactionCompensator`.**
7. **Лінія маршруту:** `TrackSimplifier` при завершенні першої поїздки + `LinearReferencer` → `kmFromStart`.
8. **`SectionClusterer` + пакет попереджень** з версією та `304`.
9. **Перегляд поїздки.**
10. **Редагування проблем** з правилом «перемагає останнє редагування», «Вже нема», відновлення, видалення.
11. **Збірка в Docker і деплой** на VPS з Caddy.
