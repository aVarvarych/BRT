# BE-20 · Перегляд поїздки

**Епік:** 5 · Попередження · **Тип:** історія · **Оцінка:** S · **Залежить від:** BE-17

## Контракт
`GET /v1/trips/:id/review` → `200`:
```json
{
  "trip": { "id": "uuid", "routeId": "uuid", "startedAt": 0, "finishedAt": 0, "distanceM": 0 },
  "marks": [{
    "markId": "uuid", "t": 0, "kmFromStart": 34.2,
    "isNew": true,
    "problem": { "...": "ProblemDTO" }
  }]
}
```
- `marks` впорядковані за `t`.
- `isNew = true`, якщо саме ця позначка створила проблему (`problem.id === markId`).
- `kmFromStart` — це відстань **уздовж треку цієї поїздки** до моменту `t`, а не вздовж лінії маршруту. На першій поїздці ці значення збігаються, але трек конкретної поїздки точніший.

## Що зробити
- Query-сервіс `ITripReviewQuery` в application, реалізація в infrastructure. Це читання, тож агрегати не потрібні.
- Відстань уздовж треку до моменту `t`: сума відрізків між точками з `t' ≤ t`.

## Критерії приймання
- [ ] Integration: поїздка з трьома позначками (дві нові, одна повторна) → правильні `isNew` і зростаючі `kmFromStart`.
- [ ] Чужа поїздка → 404.

## Підказки ментора
- Накопичену відстань можна порахувати одним SQL-запитом з віконною функцією (`SUM(ST_Distance(...)) OVER (ORDER BY t)`). Але й код на TS у query-сервісі прийнятний: це читання, а не бізнес-правило.
