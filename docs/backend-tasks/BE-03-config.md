# BE-03 · Конфігурація та її валідація

**Епік:** 0 · Каркас · **Тип:** технічна · **Оцінка:** S · **Залежить від:** BE-01

## Навіщо
Якщо застосунок запустився без `API_KEY` або з поламаним `DATABASE_URL`, це має виявитися на старті, а не з першим запитом.

## Що зробити
- `src/main/config/env.ts`: читає `process.env`, валідує й повертає **типізований** об'єкт. Якщо змінна відсутня або невалідна, процес завершується зі зрозумілим повідомленням.
  - `NODE_ENV`: `development` | `test` | `production`
  - `PORT`: за замовчуванням 3000
  - `DATABASE_URL`
  - `API_KEY`: мінімум 32 символи
  - `LOG_LEVEL`
- `src/domain/config/GeoRules.ts`: доменні пороги як **значення за замовчуванням**, з якими працюватимуть домен і юзкейси (див. PRODUCT.md §10.4):

| Параметр | Значення |
|---|---|
| `reactionDelaySec` | 1.5 |
| `matchRadiusM` | 30 |
| `sectionGapM` | 200 |
| `maxDistanceFromLineM` | 50 |
| `routeSimplifyToleranceM` | 5 |
| `sectionPolylineStepM` | 20 |

- Доменні пороги передаються сервісам через конструктор у composition root, а не імпортуються напряму. Тоді в тестах їх легко підмінити.

## Критерії приймання
- [ ] Без `API_KEY` процес не стартує, а в повідомленні сказано, якої змінної бракує.
- [ ] Unit-тест перевіряє валідацію `env` на правильних і неправильних наборах змінних.
- [ ] `.env.example` описує всі змінні.

## Підказки ментора
- Для валідації візьміть `zod` або напишіть невелику власну функцію. Головне, щоб на виході був тип, а не `string | undefined`.
- `.env` читає сам Node через `--env-file-if-exists` у скриптах `dev` / `start` (BE-01), тому бібліотека `dotenv` не потрібна. Код бачить лише `process.env`, і тільки в `env.ts`. Решта коду отримує вже типізований конфіг.
- CORS не потрібен: у dev застосунок звертається до API через проксі Vite, а в продакшні через Caddy на тому самому домені. Обидва випадки same-origin.
