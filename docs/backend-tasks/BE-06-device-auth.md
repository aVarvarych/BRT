# BE-06 · API-ключ і розпізнавання пристрою

**Епік:** 0 · Каркас · **Тип:** історія · **Оцінка:** M · **Залежить від:** BE-05

## Навіщо
Реєстрації немає (PRODUCT.md §6.4), але API відкритий в інтернет. Від сторонніх його захищає статичний ключ, а `X-Device-Id` відрізняє дані одного телефона від іншого.

## Що зробити
- **Домен:** сутність `Device`:
  - `id`;
  - `firstSeenAt`;
  - `lastSeenAt`.
- **Порт:** `IDeviceRepository` з методом `touch(id, now)`. Метод ідемпотентно створює пристрій або оновлює `lastSeenAt`.
- **Таблиця:** `devices`:
  - `id uuid pk`;
  - `first_seen_at timestamptz`;
  - `last_seen_at timestamptz`.
- **Middleware `authenticate`** (для всіх `/v1/*`):
  1. Немає `X-Api-Key` або ключ не збігається → `401 UNAUTHORIZED`. Порівнювати через `crypto.timingSafeEqual`.
  2. `X-Device-Id` відсутній або не UUID → `400 INVALID_DEVICE_ID`.
  3. Викликати `touch`, а `deviceId` покласти в контекст запиту (`res.locals.deviceId` або request context).
- `lastSeenAt` не обов'язково оновлювати на кожному запиті. Достатньо, якщо відтоді минуло понад хвилину.

## Критерії приймання
- [ ] Без ключа → 401, з неправильним ключем → 401, з правильним ключем без device id → 400.
- [ ] Перший запит з новим `X-Device-Id` створює рядок у `devices`, наступні його не дублюють.
- [ ] `/health` працює без заголовків.
- [ ] Integration-тести на всі випадки вище.

## Підказки ментора
- `timingSafeEqual` кидає помилку, якщо довжини буфери різні. Спершу порівняйте довжини, а потім уже самі значення.
- Кожен наступний юзкейс отримує `deviceId` у вхідних даних явно, а не дістає його з глобального контексту. Тоді юзкейси не залежать від HTTP.
