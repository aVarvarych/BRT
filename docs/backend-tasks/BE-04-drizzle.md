# BE-04 · Drizzle: підключення та міграції

**Епік:** 0 · Каркас · **Тип:** технічна · **Оцінка:** M · **Залежить від:** BE-02, BE-03

## Навіщо
Потрібні доступ до бази й версіоновані міграції. Схема таблиць з'являтиметься в наступних задачах.

## Що зробити
- Встановити `drizzle-orm`, драйвер `pg` (node-postgres) і `drizzle-kit`.
- `src/infrastructure/persistence/drizzle/`:
  - `client.ts` створює пул і екземпляр `drizzle` з конфігу;
  - `schema/` — тут лежатимуть таблиці (поки порожньо);
  - `migrations/` — сюди їх генерує `drizzle-kit`.
- Перша міграція виконує `CREATE EXTENSION IF NOT EXISTS postgis;`. Її пишемо вручну (custom migration).
- Скрипти:
  - `db:generate` (згенерувати міграцію зі схеми);
  - `db:migrate` (застосувати);
  - `db:studio` (за бажанням).
- Хелпер для integration-тестів: підключається до `DATABASE_URL_TEST`, накочує міграції перед прогоном і очищає таблиці між тестами (`TRUNCATE ... CASCADE`).
- **Транзакції:** порт `IUnitOfWork` в `application` з методом `run<T>(fn: () => Promise<T>): Promise<T>`. Реалізація в infrastructure тримає поточну транзакцію в `AsyncLocalStorage`, а репозиторії беруть її звідти. Схема та сама, що в medbuy, тільки без шини команд.

## Критерії приймання
- [ ] `npm run db:migrate` на чистій базі вмикає PostGIS.
- [ ] Integration-тест: юзкейс у `unitOfWork.run` кидає помилку → зміни відкочено; не кидає → збережено. Перевірити на тимчасовій тестовій таблиці або на першій реальній з BE-08.
- [ ] Пул закривається при graceful shutdown (див. BE-05).

## Підказки ментора
- Для точок простіше брати тип `geometry(Point, 4326)`. Відстань у метрах дає приведення до `::geography`. Drizzle підтримує `geometry` з коробки.
- Подумайте, чи потрібен `IUnitOfWork` у кожному юзкейсі. Насправді він потрібен лише там, де пишеться **кілька** таблиць (наприклад, прийом пакета в BE-11).
