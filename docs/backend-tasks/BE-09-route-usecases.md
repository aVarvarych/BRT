# BE-09 · Юзкейси та ендпоінти маршрутів

**Епік:** 1 · Маршрути · **Тип:** історія · **Оцінка:** M · **Залежить від:** BE-06, BE-08

## Юзкейси
| Юзкейс | Ендпоінт | Відповідь |
|---|---|---|
| `CreateRoute` | `POST /v1/routes` `{ id, name }` | `201` + RouteDTO. Якщо такий `id` уже є в **цього ж** пристрою, `200` + наявний маршрут (ідемпотентність). Якщо `id` належить іншому пристрою, `409` |
| `RenameRoute` | `PATCH /v1/routes/:id` `{ name }` | `200` + RouteDTO |
| `DeleteRoute` | `DELETE /v1/routes/:id` | `204`. Видаляє поїздки, точки, позначки й проблеми маршруту |
| `ListRoutes` | `GET /v1/routes` | `200 { routes: RouteDTO[] }`, від свіжіших до старіших за `updatedAt` |

```ts
RouteDTO = {
  id: string; name: string; createdAt: number; updatedAt: number;
  stats: { activeProblems: number; trips: number; lastTripAt: number | null; lineLengthM: number | null }
}
```

## Що зробити
- Юзкейси в `application/route/`, кожен отримує `deviceId` у вхідних даних.
- Чужий або неіснуючий маршрут → `NotFoundError` (404).
- `stats` рахує окремий **query-сервіс** (порт `IRouteStatsQuery`), а не агрегат. Поки поїздок і проблем немає, повертаються нулі. Справжній підрахунок з'явиться після BE-10 і BE-13.
- Каскадне видалення робиться через `ON DELETE CASCADE` у зовнішніх ключах наступних таблиць. Тут достатньо видалити маршрут.
- Валідація тіла запиту відбувається в presentation (zod або власний валідатор). Помилка → 400 зі списком полів у `details`.

## Критерії приймання
- [ ] Integration-тести HTTP на кожен ендпоінт, включно з чужим маршрутом (404) і повторним `POST` з тим самим `id` (200, без дубля).
- [ ] Unit-тести юзкейсів з фейковим репозиторієм.

## Підказки ментора
- Ідемпотентний `POST` потрібен, бо застосунок працює без зв'язку й може повторити запит, якщо не отримав відповідь.
- DTO будується в presentation-мапері. Агрегат нічого не знає про JSON.
